採掘の採算が合わなくなり、1 台だけ動かしていた ASIC マイナー（IceRiver AL0・公称 100 W）を、冬のあいだ 3 台に増やしました。目的は採掘ではなく**暖房**です。排気をそのまま書斎に出すなら、マイナーが使った電力はほぼ全部この部屋の熱になります。同じワット数の電気ストーブと発熱量はほぼ同じです。ただし、エアコン（ヒートポンプ）は同じ電力で 2〜4 倍の熱を外から運んでくるので、暖房の効率としてはエアコンに負けます。

珍しい発想ではありません。家庭用には採掘しながら暖めるヒーター製品があり、マイナー大手の Canaan も暖房を兼ねる小型機（[Avalon Mini 3](https://support.canaan.io/en-us/knowledgebase/article/KA-01243)）を出しています。規模は違いますが、フィンランドでは採掘設備の熱を地域の暖房網に販売した実績もあります（[MARA](https://mara.com/posts/recycling-heat-from-data-centers-to-warm-a-community-in-finland)）。この記事は、もともと暖房用ではない、止めていた機械で同じことをやり、効き目を温度計で数えた記録です。

本当に効いているのかを、家の温湿度計 4 台（書斎・寝室・居間・屋外）のログで測りました。先に結果です。

| 実測したこと（深夜 2〜5 時の平均・各 10〜12 日） | 1 台のとき | 3 台のとき |
|---|---|---|
| 書斎 | 26.1 ℃ | 27.2 ℃ |
| 屋外 | 14.7 ℃ | 11.5 ℃ |
| 書斎と屋外の差 | 11.4 ℃ | 15.7 ℃ |
| 寝室と屋外の差（比べる相手） | 5.5 ℃ | 7.0 ℃ |
| **書斎と寝室の差** | 5.9 ℃ | **8.8 ℃（+2.9 ℃）** |

外は 3.2 ℃ 冷え込んだのに、書斎は 1.1 ℃ 上がり、寝室は 1.7 ℃ 下がりました。両室の温度差は **2.9 ℃ 広がった**ことになります。増台の発熱と矛盾しない結果ですが、窓の開け閉めや部屋ごとの冷え方まで分離できた数字ではありません。この比べ方が意外と難しかったので、その手順と、機械が言うことを聞かなかった話を書きます。

## 機材

| もの | 数 | 役割 |
|---|---|---|
| IceRiver AL0 | 3 台 | 熱源。公称 100 W/台・合計 300 W・24 時間で 7.2 kWh/日 |
| 温湿度計（SwitchBot） | 4 台 | 書斎・寝室・居間・屋外（ベランダの防水型） |
| 小さなスクリプト | 1 本 | SwitchBot Cloud API を 30 分ごとに読み、JSONL に追記 |

電力計は付けていないので、電力は公称値です。AL0 自体は以前の記事で自前のフルノードにつないだもので、ハッシュレートは 3 台で 10 分平均 1,159.6 GH/s でした（[AL0 を自前 Alephium フルノードにつなぐ](https://zenn.dev/wisteriacorp/articles/wisteria-96d7811340d7)）。

温湿度のログは、API の応答をそのまま 1 行ずつ残しています（実際の 1 行から 2 台分を抜粋）。

```json
{"ts": "2026-11-20T03:00:14+09:00", "devices": [
  {"name": "書斎の温湿度計Pro", "type": "MeterPro", "status": {"temperature": 26.8, "humidity": 23}},
  {"name": "ベランダの防水温湿度計", "type": "WoIOSensor", "status": {"temperature": 11, "humidity": 48}}
]}
```

加工せずに残しておいたおかげで、あとから「どの期間と比べるか」を何度でもやり直せました。

## つまずき 1: 設定を書き換えても、機械が元のプールに居座る

増やす 2 台は、出荷時の設定で外部のマイニングプールに向いていました。管理画面で Pool 1 を自前のプールに書き換えて保存し、再起動します。ところが自前のプール側でいくら待っても接続が来ません。

プール側のホストで `tcpdump` を 140 秒取ったところ、AL0 からの SYN は**1 つも**届いていませんでした。AL0 は Pool 1 を試しもせず、Pool 2・3 に残っていた外部プールへつなぎ続けていたのです。

```bash
sudo tcpdump -ni any 'tcp port 20032 and src host 192.168.x.y'
# 140 秒・0 packets captured
```

Pool 2 も自前のプールに書き換えて再起動すると、すぐに接続が来ました。なぜ Pool 1 を飛ばすのか（最後につながったスロットを優先するのか）は確かめられていません。**増台するときは最初から Pool 1 と Pool 2 の両方を書き換える**、というのが今回の教訓です。

もう 1 つ、増やした 2 台の管理画面は**工場出荷時のログイン情報のまま**でした。LAN の中だけで使っていても、変えておくべきです。

## つまずき 2: 自動化が「1 台に戻せ」と言い続ける

この機械には、採算を毎朝判定するスクリプトが付いています。「採算割れが 3 日続いたら 1 台に戻す」という提案を出す作りなので、暖房のために 3 台にした翌朝から、毎日「戻せ」と言われます。

採算とは別の目的で動かしている機械だ、ということをスクリプトに教える必要がありました。やったことは単純で、暖房期間の終わりの日付と台数を設定に置き、期間中は下限を 3 台にしています。

```python
def rig_floor() -> int:
    """暖房期間（heating_mode_until まで）は heating_rigs を下限にし、1 台へ戻す提案を出さない。"""
    until = str(CFG.get("heating_mode_until") or "")
    if until and datetime.now(JST).strftime("%Y-%m-%d") <= until:
        return max(1, int(CFG.get("heating_rigs") or 1))
    return 1
```

増やす提案の条件（採算が十分に取れる日が 3 日続くこと）はそのままです。暖房をやめる日が来れば、何もしなくても元の判定に戻ります。

## 測る: 比べる期間で、見かけの差が倍になる

### 最初の比較（間違い）

増台した 11 月 10 日の前後で、書斎と寝室の差（深夜帯）を比べました。前は 10 月 20 日からの 19 日間です。

| | 前（10-20〜11-09） | 後（11-11〜11-22） |
|---|---|---|
| 書斎と寝室の差 | 3.1 ℃ | 8.8 ℃ |

+5.7 ℃。2 台・200 W 足しただけにしては大きすぎます。

### 段差は増台の前にあった

日ごとに並べると、理由が見えました。

| 日付 | 10-26 | 10-27 | 10-28 | **10-29** | 11-01 | 11-03 | 11-09 |
|---|---|---|---|---|---|---|---|
| 書斎と寝室の差（深夜） | −0.5 | 1.6 | 0.0 | **3.8** | 7.2 | 5.1 | 5.9 |

10 月 29 日を境に、台数は 1 台のまま、書斎だけが急に暖かくなっています。ちょうど窓を閉め始めた時期と重なります。ここを「前」に混ぜると、窓を閉めた効果まで AL0 の手柄になります。

そこで「前」を **10 月 29 日〜11 月 9 日**（窓を閉めた後・1 台）に絞りました。

### 比べ方の 3 つの工夫

1. **深夜 2〜5 時だけを使う**。日射が無く、人も寝ていて、部屋の出入りが少ない時間帯です
2. **外気との差で見る**。外が寒い日は部屋も寒いので、温度そのものではなく「屋外より何℃高いか」を比べます
3. **比べる相手の部屋を置く**。冬に向かうと、熱源の無い寝室でも屋外との差は広がります（今回 +1.5 ℃）。書斎の広がり（+4.3 ℃）からこれを引いた残りを、増台による広がりの目安にします。同じ夜どうしなら外気は引き算で消えるので、結局は「書斎と寝室の差」を見ているのと同じです。外気は「外が冷えたのに書斎は上がった」という状況を示すために使っています

```python
import json, statistics as st
from collections import defaultdict
from datetime import datetime, date

ROOMS = {"書斎": "書斎の温湿度計Pro", "寝室": "寝室の温湿度計", "屋外": "ベランダの防水温湿度計"}

def nightly(path: str) -> dict[date, dict[str, float]]:
    buf = defaultdict(lambda: defaultdict(list))
    for line in open(path, encoding="utf-8"):
        r = json.loads(line)
        ts = datetime.fromisoformat(r["ts"])
        if not 2 <= ts.hour < 5:
            continue
        for d in r["devices"]:
            t = (d.get("status") or {}).get("temperature")
            for room, name in ROOMS.items():
                if d["name"] == name and t:
                    buf[ts.date()][room].append(t)
    return {day: {k: st.mean(v) for k, v in rooms.items()}
            for day, rooms in buf.items() if len(rooms) == len(ROOMS)}

def gap(per, start, end, a, b):
    days = [d for d in per if start <= d <= end]
    return st.mean(per[d][a] - per[d][b] for d in days), len(days)
```

### 結果

| 深夜 2〜5 時 | 前（10-29〜11-09・10 日） | 後（11-11〜11-22・12 日） | 広がり |
|---|---|---|---|
| 書斎と屋外の差 | 11.4 ℃ | 15.7 ℃ | +4.3 ℃ |
| 寝室と屋外の差 | 5.5 ℃ | 7.0 ℃ | +1.5 ℃ |
| 書斎と寝室の差 | 5.9 ℃ | 8.8 ℃ | **+2.9 ℃** |

終日平均で同じことをしても、書斎と寝室の差は 6.7 → 9.4 ℃（+2.7 ℃）で、ほぼ同じ値になりました。書斎のエアコンは、後の期間の日次消費が 0.0〜0.2 kWh で、暖房には使っていません。

基準期間の始まりを動かすと、差は 10 月 20 日起点で +5.7 ℃、10 月 29 日起点で +2.9 ℃、11 月 3 日起点で +3.0 ℃ でした。比べる相手を居間にしても +3.0 ℃ です。10 月 29 日以降を基準にする限り、値はほぼ動きません。


## 限界

- 電力計が無いので、電力は公称値です。実際の消費は 1 台ずつ測る必要があります
- 在室時間は記録していません。深夜帯に絞ったのは、その代わりです
- 部屋ごとに温湿度計は 1 台で、置き場所の影響は分かりません
- 比べた期間は 10〜12 日ずつで、天気の巡り合わせの影響は残ります
- 増台は 1 回しか試していません。気温は季節とともに一方向に下がっていくので、1 台と 3 台を数夜ずつ何度か入れ替えれば、季節の変化と台数の効果を分けられます
- 窓を閉めた時期は記憶によるもので、記録はありません

## まとめ

- 採算割れのマイニング機は、暖房として使えました。1 台から 3 台（公称 +200 W）にすると、深夜の書斎と寝室の温度差は 2.9 ℃ 広がりました
- 効き目を測るなら、**生ログを残し、比べる期間に生活の変化が混ざっていないかを日ごとに見る**こと。基準期間に窓を閉める前の日を混ぜると、見かけの差は約 2 倍になりました
- 機械を増やすときは、プール設定を Pool 1 と Pool 2 の両方とも書き換え、工場出荷のログイン情報を変えること
- 自動化には「採算とは別の目的で動かしている」期間を教えておくこと
