前回、NVIDIA GB10 搭載の自宅サーバーでローカル LLM を数ヶ月運用して踏んだ罠を書きました。あの記事は「個別の穴」の話でしたが、今回は一段上の話です。**クラウド LLM（Claude）とローカル LLM（GB10 上の Ollama）をどう役割分担させ、その運用が本当に機能しているかをどう監視し、定期実行の仕組みそのものがどう静かに壊れるか**。個人で AI 基盤を組むなら、遅かれ早かれ全部ぶつかる論点だと思います。

環境だけ再掲しておきます。NVIDIA GB10・128GB ユニファイドメモリ・帯域 273GB/s の小型機を自宅 LAN に置き、Ollama で複数モデルを常駐させています。アイドル時は GPU 使用率 0%・消費電力 4.5W・メモリ使用量 4.4/121GB、load average も 0.14 程度です。つけっぱなしでも電気代はほぼ気にならない水準で、24時間稼働を前提に設計を組んでいます。

## 1. なぜローカルに寄せるのか

ローカル LLM 導入の動機としてよく語られるのは「プライバシー」「コスト」「オフライン動作」の3つです。自分の場合、投入のきっかけは完全に**コスト**でした。クラウド LLM の利用量が増え続け、このままでは運用コストが青天井になる予感がしたので、肩代わりできる作業をローカルに逃がす設計を始めました。プライバシーは副産物として付いてきたもので、オフライン動作に至ってはほぼ使っていません。動機を最初から分けて意識しておくと、後で「枠が余っているのに無理にローカルへ逃がす」という逆転判断を防げます。あくまでコストが詰まってきたときだけローカルへ回す、という向きの運用です。

ここで一つ注意が要ります。ローカルに「寄せた」つもりでも、モデル一覧に「Cloud」と名の付く選択肢が並んでいることがあり、これを選ぶとデータは手元で完結せず外部のサーバーへ送信されます。名前だけ見るとローカル実行に見えるので、機密性目的で選ぶときは実際に推論がどこで行われているかを確認したほうがいいです。見た目のローカル感と実際の秘匿性は、思ったよりあっさりずれます。

もう一つ、数字に出ない代償があります。高性能機でもローカル LLM を常用するとファンが回りっぱなしになり、作業機としての使用感が明確に落ちます。これは電気代の話ではなく、常用するかどうかはベンチマークのスコアではなく「並行作業への干渉」で決まる、という話です。自分も一時期、常用の不快感から有料サブスクリプションに後戻りしかけました。「無料であること」の価格は、思ったところについていないものです。

## 2. 振り分けの設計原則 — 答えが入力にあるか、判断が要るか

役割分担のルールは単純です。**答えが入力に文字どおり存在していて、作業が機械的な圧縮で済むならローカル。文脈照合や価値判断が要るならクラウド。** これだけです。

もう少し厳密に言うと、分かれ目は「仕事の種類」でも「入力データの種類」でもなく、**配置**です。ローカル LLM の出力が下流にとって唯一の入力になる配置は、実質的に判断を丸投げしている状態で危険です。欠落があっても誰も気づけず、誤りがあっても誰も検知できません。逆に、原文が常に隣にあって、ローカル LLM の出力は「どこを読むべきかの索引」としてしか使われない配置なら、機械的圧縮として安全に機能します。欠落は原文を読めば埋まり、誤りは突き合わせれば落ちます。同じモデル・同じ要約というタスクでも、この配置の違いだけで性質が反転するのが面白いところです。

この軸に沿って、自分の環境でローカルとクラウドをどう割り振っているかを一覧にすると次のようになります。

| 仕事の性質 | 向く場所 | 理由 |
|---|---|---|
| 領収書の店名・金額・日付をそのまま拾う | ローカル | 答えが画像に literal に存在する |
| ホビー用途の画像から文字を読む | ローカル | 同上。誤読は軽微で後段の人手確認が前提 |
| 音声を文字に起こす | ローカル | ASR は決定論的な変換作業 |
| 自分のメモ群を検索して質問に答える | ローカル（出典つき） | 出典が必ず併記され裏取りできる＝索引止まり |
| 何が重要かを判断する／書く／決める | クラウド | 文脈照合と価値判断が要る |

表の下2行がこの軸をそのまま体現しています。メモ検索は出典という形で「原文併存」を強制しているので機械的圧縮の側に置け、判断・執筆は原文があっても判断そのものを委譲できないのでクラウド側に残る、という切り分けです。

この軸を持つ前は「画像や音声ならローカル、テキストならクラウド」という入力の種類で分けようとしていました。これは筋が悪く、たとえば同じ画像入力でも「レシートの文字を拾う」のと「この資料に何が足りないかを評価させる」のとでは要求される能力がまったく違います。前者は literal な抽出で後者は評価という判断です。入力の形式ではなく、求めている答えの性質で分けないと、ローカル LLM に不向きな仕事を気づかないまま渡し続けることになります。

## 3. ローカルに任せている仕事の実例

### 3-1. 領収書 OCR

ScanSnap の ADF 両面スキャナが監視フォルダへ落とした PDF/JPEG を、ローカルのビジョンモデル（qwen2.5vl:32b）が店名・日付・金額・税額・支払手段・カテゴリ・明細・登録番号まで構造化します。検証用の合成レシートで試したところ、店名「まいばすけっと 田町駅前店」・日付・合計930円・税68円・支払手段・品目4点・登録番号まで**全項目が正答**でした。領収書という機微データがクラウドに一切出ない上に、クラウド LLM のトークンも消費しません。生成されたドラフトはあくまで下書き扱いで、最終的な金額確定は自分の目で見てから、というルールにしています。

### 3-2. 画像読解のベンチマーク

同じビジョンモデルの軽量版（qwen2.5vl:7b）で、手元のホビー用途の画像（ゲームのアイテムカードなど）から日本語の固有名詞を読ませたところ、21秒で正確に認識できました。ただし軽量版はゲームタイトル名を軽微に誤認することがあり、実例としてまったく別の既存タイトル名を返してきたケースがありました。精度が要る抽出には上位モデル（32b）を使う、という使い分けをしています。軽量モデルは速いが細部で踏み外す、重いモデルは遅いが堅実、という当たり前の結論ではありますが、実測して初めて「どこまで軽量版に任せていいか」の線が引けました。

### 3-3. 音声メモの音声認識ベンチマーク

この GB10 機でも faster-whisper を動かしていますが、ここで一つ発見がありました。**CUDA が ARM+Blackwell 構成を認識せず、推論は CPU で動きます。** それでも Grace の20コアがあるため、base モデルで実測 14倍速という速度が出ます。公開されているテスト音声（英語11秒のサンプル）を認識させたところ、モデルロード込みで5.4秒、内容も正確でした。日本語の精度を求める場合は medium か large-v3 を使う必要があります。これはあくまで音声メモ・サンプル音声の速度ベンチマークであって、生活や仕事の音声を扱うものではありません。CPU 推論でもここまで出るなら、GPU が効かない構成を「使えない」と即断する前に、コア数とモデルサイズの組み合わせで実測する価値はあると思います。

### 3-4. 自分のメモ群へのローカル質問応答

手元の約9,600件のノートをローカルで埋め込み索引化し、質問に対して関連ノート上位を検索・ローカル LLM が出典付きで回答する、という「第二の脳」を作っています。あるクエリでは関連ノート6件を検索し、34秒で出典つきの回答が返ってきました。無料・無制限・LAN 内完結で、クラウド LLM のトークンも一切使いません。ハルシネーションが起きても出典を辿れば検証できる設計で、これも2章の軸でいえば「索引止まり」の配置に収まっています。回答そのものを鵜呑みにせず、添えられた出典を自分で開く手間を省略しない、というのがここでの唯一の運用ルールです。

### 3-5. 常時アクセスできる私的アシスタント

ChatGPT 風の UI（Open WebUI）を Docker コンテナとして自宅 LAN 内に常駐させ、PC・スマホから常時アクセスできるようにしました。思いつきの質問や下書き、画像の読解をクラウド LLM を介さず無制限・秘匿でこなせます。履歴は Docker のボリュームにローカル保存され、外へは出ません。深夜に思いついた雑な質問をクラウド LLM の枠を気にせず投げられる、という体験の変化は数字には出ませんが、運用していて一番効いている部分かもしれません。

## 4. 監視設計 — 「動いている」と「使われている」は別問題

ここからが本題です。ローカル LLM の仕組みを一通り組んだあと、ある時「効果が実感できない」という感覚に襲われました。原因を調べると、**ローカル LLM は正常に稼働していて、問題は生成物が自分の動線に一本も載っていなかったこと**でした。機能を積み上げることと、積み上げた機能が実際に消費されることは、まったく別の問題です。

ローカル LLM の価値の大半は「クラウド LLM のトークン節約」です。これは体験としては何も変わらないので、節約額にメーターを付けないと、節約していること自体が存在しないのと同じになります。生成しただけで満足し、翌日以降その生成物を誰も開かない、という状態は GPU の無駄打ちと同じです。しかも「動いているのに実感がない」という、故障よりもたちの悪い状態を生みます。壊れていれば直せばいいのですが、動いているのに価値が見えないものは、直す対象にすら気づけません。

さらに厄介なのは、その「稼働メーター」自体が静かに劣化することです。ローカル LLM を呼ぶスクリプトを増やすたびにメーター側の集計対象リストを更新しないと、新しいスクリプトの生成物がカウントから漏れます。実際に自分の環境では、集計対象が実働スクリプトの一部しか登録されておらず、表示上「5件・約17,000字」だったところ、実測すると「49件・約228,000字」——**約13倍の過小表示**でした。可視化の仕組み自体が可視化されていなかった、という再帰的な穴です。

もう一つの劣化パターンは、生成物の frontmatter に書くタグの表記が割れてしまうことです。あるスクリプト群と別のスクリプト群とで、同じ意味のタグに別の表記を使っていたため、集計スクリプトが片方しか見ていないと、ファイルが存在するのに**件数だけ静かに0件**になります。新しいローカル処理を足すたびに「集計対象のリストを更新したか」「タグの表記は既存と揃っているか」を確認する、という地味な規律がないと、この手の過小表示は何度でも再発します。メーターは一度作って終わりではなく、作った時点の網羅率で固定され、新しい処理を足すたびに静かに古びていくものだ、と考えるようになりました。

加えて、そもそも件数や文字数という形に乗らない生成物もあります。ファイルを新規作成せず既存のフロントマターへ注記するだけの処理や、出力先がノートではなく内部の状態ファイルである処理は、ファイル数を数える方式のメーターには原理的に引っかかりません。こうした「構造的に測れないもの」は無理にメーターへ押し込もうとせず、別経路で存在を把握しておく、という割り切りも必要でした。

## 5. 定期実行の失敗学 — `exit 0` は成功の証拠にならない

ローカル LLM 周りの処理は大半を Windows のタスクスケジューラで定期実行しています。現在86件のタスクが動いていますが、そのうち80件は共通の非表示ランチャー経由で起動し、コンソール窓を一切出しません。これは見た目の話ですが、ここから先は「動いているように見えて実は何もしていない」という失敗の集合体でした。

| 罠 | 症状 | 対処 |
|---|---|---|
| 固定日トリガー＋祝日ガード | 実行日が土日祝に重なった回が**延期ではなく消滅**する。ある月次タスクでは実行日が土曜に当たり、その月の成果物が存在しないまま19日間気づかれなかった。年間で見ると7か月に約2回の頻度で月次成果物が失われる計算になる | 固定日・固定曜日トリガーをやめ、**毎日起動＋成果物の実在チェックで冪等に判定**する設計へ変更。週次タスクも同型の被害があり同じ対処をした |
| `LastTaskResult=0` 過信 | exit code が0でも「何かした証拠」にはならない。実際に起きた障害3件は全てexit 0で終わっており、従来の監視ではどれも検出できなかった | タスクが触るはずのログ領域が実際に更新されたかを別途チェックする仕組みを足す |
| S4Uログオン | 対話ログオンなしで動くタスクは、資格情報マネージャーに保存した認証情報を読めない（復号鍵が対話ログオン時にしか解錠されないため）。あるバックアップタスクはこれが原因で4回連続無言スキップし、一度もファイルを転送していなかった | SMB 共有へ書き込むタスクは対話ログオン型にする |
| sshのハング | リモート処理でsshが応答待ちのまま固まると、タスクの実行インスタンスごと居残る。3日間放置したら4世代のゾンビプロセスが生存していた。接続タイムアウトの設定は認証成立後のハングには効かない | keepalive 系オプションを明示的に追加し、無応答を一定時間で強制終了させる |
| PowerShellのBOM | 日本語を含む`.ps1`にBOMを付けずに保存すると、PowerShell 5.1が別のエンコーディングとして誤読し、日本語バイト列が引用符や括弧に化けて構文エラーになる。コメント内なら通ることもあるが運任せ | 日本語を含むスクリプトは必ずBOM付きUTF-8で保存する |
| bare pythonの化け | 環境によって`python`コマンドの解決先が意図しない別の仮想環境に化け、必要なモジュールが無く`ModuleNotFoundError`で**無言のまま死ぬ**ことがある。「昨日動いたのに今日動かない」の正体の一つだった | Pythonの実行パスをインタプリタごと絶対パスで固定する |

共通して言えるのは、**どの罠も `rc=0` のまま起きている**ということです。前回の記事で書いた「静かすぎる失敗」は推論の中身の話でしたが、今回のそれは実行基盤の話で、同じ病名が別の層にも転移していました。判定を「実行できたか」ではなく「成果物が実在するか」に置き換える、というのが結局いちばん効く処方箋でした。

個人の自動化を何十本も積み上げてみて分かったのは、罠の数そのものより「罠の見つけ方」のほうが資産になるということです。固定スケジュールと祝日・休日の組み合わせ、認証方式とログオン種別の組み合わせ、文字コードとツールのバージョンの組み合わせ——どれも単体では当たり前の仕様で、組み合わさったときだけ無言で壊れます。新しい定期タスクを足すたびに、この3種類の組み合わせを一通り疑うだけで、再発の大半は防げる感触があります。

## まとめ

個人の AI 基盤を設計するときに効いた原則は、結局この3つに集約されます。

1. **振り分けは「答えが入力にあるか」で決める。** 機械的な抽出はローカル、判断が要る仕事はクラウド。ローカルの出力が下流にとって唯一の入力になっていないかを常に疑う
2. **生成量ではなく消費量を測る。** メーター自体も劣化するので、新しい処理を足すたびにメーターの対象リストも同じコミットで更新する
3. **`exit 0` を信用しない。** 実行できたかではなく、成果物が実在するかで判定する

どれも特別な技術ではなく、地味な点検項目の積み重ねです。ただ、この地味さを飛ばして機能だけを積み上げると、3章・4章・5章で書いたような「動いているのに価値が見えない」状態に必ず行き着く、というのが数ヶ月運用しての実感です。

ローカル LLM は魔法の箱ではなく、素直に力仕事をさせる相棒です。その代わり、力仕事を任せた分だけ、任せた仕組みの健全性を自分で監視する責任が増えます。アイドル4.5Wで常駐する小型機が、思ったより静かに仕事をしてくれる生活は、一度始めると手放せません。
