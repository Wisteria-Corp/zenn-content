NVIDIA GB10 が載った Lenovo ThinkStation PGX で、ローカルLLMを数ヶ月ほぼ毎日動かしています。常駐エージェントと夜間バッチと、たまに VLM で OCR。128GB のユニファイドメモリに惹かれて買いました。

で、この記事はベンチマーク記事ではないです。スペックの数字は他の人が書いてくれているので、こっちは運用していて実際に踏んだ穴の記録を書きます。順不同ではなく、被害がわかりにくかった順。最後に、罠を調べているうちに転がり込んできた小さな実験の話があって、たぶんそこが一番おもしろいです。

環境だけ先に。

- Lenovo ThinkStation PGX（GB10 / 128GB unified / 帯域273GB/s / DGX OS・ARM64）
- Ollama で gpt-oss:120b、qwen3:30b-a3b、VLM 数種
- アイドル実測 4.5W・GPU 0%。つけっぱなしでも財布が痛まないのは正義です

128GB の何が嬉しいかというと、gpt-oss:120b（実測 64.7GB）を常駐させたまま qwen3:30b-a3b（44.9GB）を同居させられること。合計 109.6GB。ただし3本目を要求した瞬間に全員退去して、戻すのに19秒かかります。この「同居の限界」も後で罠として出てきます。

## 罠1. thinking × format:json で出力が丸ごと消える

JSONモードで構造化出力をさせたら、response が空文字で返ってきました。HTTP 200、例外なし、exit code 0、処理時間もそれらしい。ログを何往復見ても「正常」なんですよ。空の結果だけが静かに下流に流れていく。

原因は thinking 対応モデルとの組み合わせでした。生成トークンがまず thinking 側に流れる仕様と JSON 強制がかち合うと、出力が丸ごと thinking に吸い込まれて response が空になるパターンがある。

対処はふたつ。thinking を切るか、response だけ見るのをやめて thinking 込みでパースする層を挟むか。あとどちらにしても「空の成功」を弾くアサーションは入れてください。この記事の罠、半分くらいは正体が「rc=0 で空」です。

## 罠2. num_ctx 超過は先頭から静かに消える

長文を渡すと、なぜか指示に従わない。プロンプトの先頭に置いた指示や用語辞書が無視される。モデルが劣化したのかと疑うやつですが、違います。コンテキストを超えた分が古い側——つまりプロンプト先頭——から黙って捨てられているだけです。エラーは出ません。出力は一見それらしいまま。

しかもこれ、二重底になっていて、OpenAI 互換の `/v1` を素で叩くと、モデル自体は 131,072 の窓を持っていてもサーバー既定の 65,536 で頭打ちになります。num_ctx をリクエストごとに明示しないとフル窓は使えない。

私は `prompt_eval_count` をログに出して、送ったつもりのトークン数と毎回突き合わせるようにしました。地味ですが、これで「静かに切られた」が見えるようになります。

## 罠3. reasoning_effort=high にしたら全滅した

定型文書から8項目を抜くタスクでの実測です。

| reasoning_effort | 所要 | 結果 |
|---|---:|---|
| 無指定 | 22秒 | 最良 |
| low | 12秒 | 一部取りこぼし |
| high | 48秒 | 0/8。空応答 |

high、時間を4倍かけて空を返してきました。推論トークンが予算を食い潰して出力に届かない、罠1と同じ構造です。「精度が欲しければ effort を上げる」という直感は、少なくとも抽出系では裏切られました。無指定が一番いいって何なんですかね。

## 罠4. max_tokens をケチると「空の正常終了」

短い話です。推論型モデルは見た目の出力の何倍もトークンを食うので、max_tokens が小さいと推論だけで使い切って `finish_reason: length`・content 空で正常終了します。例外なし。

なんでこんな当たり前のことをわざわざ書くかというと、後述の実験で私はこれを自分で踏んだからです。知っていても踏む。だから仕組みで守る。

## 罠5. native API か OpenAI 互換か、繋ぎ先で壊れ方が変わる

OpenAI 互換クライアント（SDK や OSS ツール）を Ollama の native `/api/chat` に向けると JSONDecodeError で必ず死にます。ストリーミング形式が違うので。`/v1` に向ければ通る。設定1行の差で「必ず壊れる/必ず通る」が分かれます。

逆に、num_ctx や seed みたいな options を細かく制御したければ native のほうが素直です。罠2の 65,536 頭打ちは `/v1` 側の話。つまり罠が経路別に分布しているので、どのスクリプトがどっちを叩くか決めて書き残しておかないと、あとで自分が混乱します（しました）。

## 罠6. 日本語の固有名詞が「バイト列のまま」出てくる

これは初見で目を疑いました。出力の中で、日本語の固有名詞だけが `æ—¥æœ¬èªž` みたいな姿で出てくる。ちなみにこれは「日本語」の UTF-8 バイト列を Latin-1 として読んだ姿です。

普通ならエンコーディングバグを疑いますよね。疑いました。HTTP 層、subprocess、ファイル I/O、全部調べて全部シロ。最終的にわかったのは、モデルの出力自体がその壊れた形で生成されているということでした。学習データ由来と思われる、モデル内部の破損モードです。よりによって壊れるのが固有名詞、つまり一番壊れてほしくない場所なのが嫌らしい。

対処は出力の後段に逆変換の修復層を挟むこと。

```python
def fix_mojibake(s: str) -> str:
    try:
        fixed = s.encode("latin-1").decode("utf-8")
        if count_cjk(fixed) > count_cjk(s):  # 日本語が増えた時だけ採用
            return fixed
    except (UnicodeEncodeError, UnicodeDecodeError):
        pass
    return s
```

おまけの教訓。この修復層を共通関数に入れて安心していたら、payload を自前で組んでいる別スクリプトが1本あって、そっちには当たっていませんでした。「共通層に入れた」と「全経路が共通層を通っている」は別の命題です。

## 罠7. VRAM を食い潰すのはモデルではなく num_ctx だったりする

VLM をデフォルト設定でロードしたら 90.4GB 要求されました。モデル本体の4倍以上。犯人は既定の num_ctx=262,144 で、KV キャッシュがモデルより重くなっていた。16,384 に絞ったら 24.5GB。

一方で LLM 側の gpt-oss:120b は、num_ctx を 32k/64k/128k と振っても常駐サイズがほぼ変わりません（重みが支配的なので）。「メモリを空けたければコンテキストを削る」が効く場所と効かない場所がある、というのが実測の答えです。冒頭に書いた 120B+30B の同居は、VLM 側の num_ctx を絞って初めて成立しました。

## 罠8. 「たまに遅い」の正体

Ollama は未使用数分でモデルを自動アンロードします。次のリクエストは再ロード19秒＋ウォームアップ。「普段は速いのにたまに異様に遅い」の大半はこれでした。常駐させるか、初回の遅さを許容するか、用途ごとに決めて keep_alive を固定する。それだけの話ですが、知らないと「不安定なマシン」という誤った印象だけが残ります。

## 罠9. 思考時間が対話を殺す。ついでに自分のベンチも汚した

"ok" 相当の一言を投げたときの応答時間。

- gpt-oss:120b（推論型MoE）: **34.9秒**
- qwen3:30b-a3b: 3.6秒

生成自体は 120b でも速いんです。遅いのは思考時間で、しかもエージェント用途だとツール呼び出しのたびに毎回発生する。思考時間 × ツール回数で平気で数分に膨れます。うちでは結局、投げて待つバッチは 120b、対話は 30b という役割分担に落ち着きました。

ついでに恥ずかしい話をひとつ。モデル移行後のベンチで「8倍遅くなった」と誤報しかけたことがあります。原因は、直前に自分がモデルの退去テストを繰り返していたこと。19秒 × 数回の再ロードが計測に乗っていただけでした。以来、性能の判断は単発計測ではなく、負荷条件が本番そのものである定期ジョブの実績ログで見ることにしています。

## 罠10. 壊れて「見える」だけ、もある

罠6は本当にモデル出力が壊れる話でしたが、逆もあります。

- Windows で stdout をパイプすると cp932 で化ける（`-X utf8` で解決）
- PowerShell 5.1 の Get-Content は、正常な UTF-8 ファイルを既定エンコーディングの都合で化けて表示することがある

私はこれで一度、正常なファイル群を「破損した」と誤診しました。本物の破損（罠6）と表示だけの化け（罠10)が同じ環境に同居していると、切り分けを間違えます。破損かどうかの最終判定はバイト列で。ターミナルの見た目を信用しない。

## おまけの実験: temperature 0 なのに出力が変わる、の正体

ここからが書きたかった話です。

llama.cpp の開発の中で、MoE モデルは貪欲デコード（temperature 0）でも実行間で出力が揺れる、という報告があります。少なくとも OpenCL バックエンドでの実測で、同一入力5回で2〜3通り。うちの運用モデルは全部 MoE です。CUDA ではどうなのか、気になったので深夜に測りました。

### まず素朴に8回投げる

native `/api/chat`、temperature 0 明示、seed 固定、逐次実行、同一の日本語プロンプト。これを gpt-oss:120b（MoE）、qwen3:30b-a3b（MoE）、対照として dense の gemma4:31b に8回ずつ。

結果が妙でした。

- gpt-oss:120b — 初回だけ別の出力。2〜8回目は7回連続でハッシュ完全一致
- qwen3:30b-a3b — 初回と、途中の1回（異様に時間がかかった回）だけ別。他は一致
- gemma4:31b（dense）— **dense なのに**初回だけ別

「MoEだから揺れる」説なら dense は揺れないはずです。揺れました。しかも3モデル全部が「ロード直後の初回だけ違う」という同じ形。これは乱数の顔ではなく、状態の顔をしています。

gpt-oss の分岐点を見ると、thinking は8回とも完全一致のまま、content の44文字目で「取得し」と「測定し」に割れて、そこから先が丸ごと変わっていました（生成トークン数も 510 と 496 に分かれる）。ほぼ同確率の2トークンが、ごくわずかな数値差でひっくり返った形です。

ちなみにこの実験、qwen3 と gemma の content が全部空でハッシュが全 run 同じ値になっていて、一瞬「完全一致！」と喜びました。よく見たらそれ、空文字列の SHA-256（e3b0c442…）なんですよ。num_predict:512 が thinking に全部食われていた。罠4を、罠の記事を書くための実験で踏むという体験ができます。

### 状態を制御して測り直す

仮説は「出力は（モデル・入力・KVキャッシュ状態）の決定的関数」。unload と別プロンプトで状態を操作します。

```
unload → cold-A → warm-A ×2 → unload → cold-A → warm-A ×2 → B → A ×2
```

結果（gpt-oss:120b）:

| 検証 | 結果 |
|---|---|
| cold と cold は一致するか | 一致（2回とも同一ハッシュ） |
| warm と warm は一致するか | 一致（4回とも同一ハッシュ） |
| cold と warm は一致するか | **不一致**。確定的に2変種 |
| 別プロンプトBを挟んだ直後のA | **cold 変種に戻る**。その次のAは warm 変種 |

きれいに割れました。同じ状態なら bit 単位で再現する。状態が違えば違う出力になる。そしてその遷移すら再現する。計26リクエストで、真の意味でランダムな揺れはゼロでした。

解釈はこうです。同じプロンプトを直前に処理したかどうかで、プロンプト評価の経路（フルの prefill か、キャッシュ再利用か）が変わる。経路が変われば浮動小数点の丸めがわずかに変わり、logits がわずかに変わり、近接確率のトークンがひっくり返り、そこから先がカスケードする。Phase 1 で qwen3 が1回だけ揺れた件も、あとで調べたら定時バッチがちょうどキャッシュを撹乱した時間帯で、この説明で辻褄が合いました。

実務的な結論はひとつだけ。**モデルや設定の単発A/B比較をするときは、捨て回を1回流してウォーム状態を揃えてから測る。** 揃えないと、設定の差ではなくキャッシュ状態の差を測ることになります。私自身、過去にやった effort 比較がどっちの状態で走ったか記録していなくて、頭を抱えました。

限界も書いておくと、これは1プロンプト・1ハード・逐次実行での結果です。並行リクエストが飛ぶ環境（continuous batching）には別の揺れ要因が知られているので、そこは別の話。

## まとめ、というか設計原則

10個並べて気づくのは、派手にクラッシュした罠がひとつもないことです。全部 rc=0。全部「一見正常」。空・切り捨て・化け・状態差が、成功の顔をして混ざってくる。ローカルLLM運用の敵はエラーではなく、**静かすぎる失敗**でした。

なのでうちの設計原則は2つだけです。「空の成功」を検知するアサーションをすべての経路に入れること。そして、ローカルLLMには長文の下読み・翻訳・分類・OCRみたいな力業だけを任せて、判断はさせないこと。要約を原文の代わりにした瞬間、静かな失敗がそのまま真実として定着します。原文が下流に残る配置でだけ使う。

……と偉そうに書きましたが、罠4はこの記事の実験でも踏んでいます。GB10 自体はいい買い物です。アイドル4.5Wで120Bが常駐している生活は、一度始めると戻れません。運用設計の全体は次(有料の予定)でまとめて書きます。
