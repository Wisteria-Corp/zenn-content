NVIDIA GB10（128GB ユニファイドメモリ）のマシン 1 台でローカル LLM を常時動かし、クラウドの LLM と組み合わせて、個人の自動化を 3 か月半ほど回しています。以前の記事では、振り分けの考え方を言葉で書きました（[個人 AI 基盤の設計](https://zenn.dev/wisteriacorp/articles/wisteria-47f423fb1c16)）。今回は**数字で振り分けを決める**ために、同じ仕事をローカルとクラウドの 6 方式に投げ、正解率・時間・電力・料金を同じ表に並べました。

| 実測したこと | 値 |
|---|---|
| 監視アラートの一次切り分け（約 3 か月・1,267 件） | ローカルで完了 **98.0%**／クラウドに上げたのは **7 回** |
| 構造化 1 文あたりの GPU 電力（ローカル 120B） | **0.150 Wh**（8B は 0.012 Wh） |
| 構造化 1 文あたりの料金（クラウド） | gpt-4o-mini 約 $0.00010／gpt-4.1 約 $0.0015 |
| 曜日計算を含む抽出 19 項目の最高点 | **ルール 19/19**。LLM は最高でも 18/19 |
| 120B ローカルと gpt-4.1 の比較 | 正解は同点（17/19）、時間は **約 14 倍**かかる |

## 構成 — 3 層で、上に行くほど高くて遅い

```
① 決定論（Python）   事実を確定する：件数・日付・再発回数・しきい値
        ↓ 判断が要るものだけ
② ローカル LLM（GB10） 一次処理：分類・下読み・一次所見。無料・待てる仕事
        ↓ escalate=true / 処理できなかったもの
③ クラウド LLM        判断・最終文書。速いが従量課金
```

ポイントは **① を LLM の前に置く**ことです。LLM に「何回目の発報か」「来週火曜は何日か」を考えさせず、Python が確定した値を渡します。LLM が担当するのは、確定した事実をどう読むかだけです。

ローカルのモデルは Ollama で動かしています。GB10 はメモリ帯域が 273GB/s なので、密な 70B より、アクティブなパラメータが少ない MoE の 120B（gpt-oss:120b）のほうが実用的な速さになります（[GB10 で踏んだ罠](https://zenn.dev/wisteriacorp/articles/wisteria-737d5801a0b3)）。

## 実測 A: 監視アラートの 3 層 — 98% はローカルで終わる

自宅のサーバー群を Zabbix で監視していて、発報は 15 分ごとにローカル LLM が一次切り分けします。流れはこうです。

1. Python が発報を集め、再発回数・フラッピング・確認済みかどうかを**確定**する
2. ローカル LLM（gpt-oss:120b）が、確定した事実を渡されて「実影響の大きさ・推定原因・初動」を書く。上に送るべきだと判断したら `escalate=true` を付ける
3. `escalate=true` のものと、ローカルが処理できずに残ったものだけ、1 日 2 回クラウドが再トリアージする

発報ログを集計すると、こうなりました。

| 区分 | 件数 |
|---|---|
| 一次切り分けの対象 | 1,267 |
| ローカルで完了 | **1,242（98.0%）** |
| ローカルで処理できず保留 | 25 |
| クラウドでの再トリアージ | **7 回** |

クラウドに上がったのは「自動起動のはずのサービスが止まったまま、理由がわからない」「再起動の理由が不明で、派生した停止が残っている」のような、**原因を推理する必要がある**ものでした。「メモリが 30 分しきい値を超えた」のような定型の発報は、ローカルの一次所見で足ります。

ローカルの所見には、必ずこの注記を付けています。

> 再発回数・フラッピング判定・確認済みかどうかは Python が確定した事実。推定原因と初動手順はローカル LLM の出力であり、固有名詞・数値は裏取りするまで確定しない。

## 実測 B: 同じ仕事を 6 方式に投げる

### 課題

音声メモを予定とタスクの JSON にする構造化です（AmiVoice で音声メモを予定に変える CLI の一部）。6 文で、日付・時刻・金額・取引先（すべて架空）の 19 項目を採点します。基準日は 2026-11-07（土）で、「来週火曜」「金曜」「月末」を日付に直す必要があります。

```text
来週火曜の十四時から、青嵐精機さんと打ち合わせです。提案書は十六ページで確定しました。
月曜と水曜はKTSラボの定例です。木曜は休みにしてください。
KTSラボから金曜に請求書が届く予定です。金額は四十五万円、支払いは月末です。
（ほか 3 文）
```

LLM はすべてtemperature 0・JSON 出力指定で、プロンプトも同じです。基準日と「週は月曜始まり」を渡しています。採点スクリプトは公開しています（`samples/compare_llm.py`・https://github.com/Wisteria-Corp/voicememo-amivoice ）。

### 結果

| 方式 | 正解（1 回目/2 回目） | 誤った日付 | 1 文あたり | 1 文あたりの料金・電力 |
|---|---|---|---|---|
| ルール（正規表現＋暦計算） | **19/19** | **0** | 0.00 秒 | — |
| gpt-4.1-mini | 18/19・17/19 | 1 | 2.1〜3.1 秒 | 約 $0.00026 |
| gpt-4.1 | 17/19・17/19 | 2 | 1.6〜1.7 秒 | 約 $0.0015 |
| gpt-oss:120b（GB10） | 17/19・16/19 | 2 | 21.8〜24.8 秒 | GPU 0.150 Wh |
| gpt-4o-mini | 14/19・13/19 | 5 | 3.1〜3.3 秒 | 約 $0.00010 |
| qwen3-vl:8b（GB10） | 4/19・5/19 | 3 | 1.8〜5.3 秒 | GPU 0.012 Wh |

- 料金は公式の単価表（Standard・1M トークンあたり 4o-mini $0.15/$0.60、4.1-mini $0.40/$1.60、4.1 $2.00/$8.00）と、実際の入出力トークン数（6 文で入力 949、出力 742〜872）から計算しました
- 電力は `nvidia-smi` で GPU ボード電力を 0.5 秒ごとに取り、推論の区間で積分しました。**GPU ボードだけで、システム全体ではありません**。アイドル時は 7.8 W、推論中は 8B も 120B も約 25 W でした

```bash
nvidia-smi --query-gpu=power.draw --format=csv,noheader,nounits -lms 500
```

### 読み取れること

**1. 曜日計算は、クラウドの上位モデルでも満点になりません。** gpt-4.1 は 2 件、日付を誤りました。120B は「月曜と水曜は定例です」を**先週の**月曜と水曜にしました。JSON の形式も日付の書式も正しいので、目で見ないと気づきません。こういう仕事は ① の決定論に置きます。

**2. ローカル 120B は gpt-4.1 と同点で、約 14 倍遅いです。** 遅さは、待てる仕事なら問題になりません。夜間のバッチや 15 分ごとの監視はローカルで回し、人が画面の前で待つ対話はクラウドに置く、という振り分けの根拠になります。

**3. 小さいモデルは速いぶん、外し方が危険です。** 8B は文にない「10:00」を補って予定を作りました。予定表に存在しない会議が入ります。

**4. temperature 0 でも、再実行で点数が変わります。** 120B は 17→16、8B は 4→5、gpt-4o-mini は 14→13 でした。ローカルだけでなくクラウドでも起きます（ローカルで揺れる原因は [KV キャッシュの決定性の実測](https://zenn.dev/wisteriacorp/articles/wisteria-a9236a633d6c) で調べました）。合否の判定を LLM の出力に置かず、① の側に置く理由です。

## 実測 C: ローカルに要約を任せて、やめた仕事と残した仕事

動画の自動字幕（約 9,000 字）を、ローカル 120B に下読みさせて要約にする処理を回していました。要約を原文と全数突き合わせたところ、劣化の型が 3 つ出ました。

| 型 | 起きたこと |
|---|---|
| 欠落の偏り | 要約 7〜8 項目に対し、原文からは 13 の論点が立った。**一般論は残り、発信者に固有の踏み込んだ主張から落ちる** |
| 手順の捏造 | テンプレートの「具体的な手順」の見出しを埋めるために、原文にない操作手順を書いた。字幕に一度も出てこないコマンド構文を 4 行分書いた例もある |
| 誤変換の伝播 | 字幕の誤変換（「上流系」→「蒸流系」、「解像度」→「改造度」）を、主張の言葉としてそのまま使う |

3 つとも、**文字化けではなく正しく読める日本語**で出てきます。形式のチェックでは捕まりません。

それでもこの処理は残しています。残した条件は 1 つで、**原文が手元に必ず残っていて、下流（クラウド側）がそれを開くこと**です。要約は「どこを読むか」を示す索引として扱い、主張は原文で確定します。要約の冒頭には「この要約を唯一の入力にしないこと」と書いて、下流の手順にも原文を読む工程を必須で入れました。

一方、下流が原文を開かない前提で使っていた別の要約処理は、入れても最終成果物の質が変わらなかったので、やめました。下流のクラウド側が、結局ほぼ全部を原文から拾い直していたためです。

## 振り分けの物差し 3 つ

ここまでの実測から、仕事を 3 層のどこに置くかを次の順で決めています。

1. **答えが入力の中にあるか。** あるなら（件数・日付・金額・店名）、まず ① の決定論で取れないか考える。取れないものだけ LLM に回す
2. **外したときに気づけるか。** 原文と突き合わせられる、後段で人かクラウドが見る、なら ② ローカルに置ける。**静かに外して、誰も気づけない仕事**はローカルに出さない
3. **待てるか。** 待てるならローカル（今回の実測で 1 文 0.15 Wh・約 22〜25 秒）。待てないならクラウド（1 文 約 2 秒・$0.0003〜$0.0015）

3 は最後の物差しです。精度と気づきやすさで置き場所が決まらないときに、時間と料金で決めます。

## 構想 — 次に変えること

- **② から ③ へ上げる条件を数える**: 今は ローカル LLM が自分で `escalate` を付けています。保留になった 25 件を分類して、「ローカルが自信を持てない」パターンを ① のルールで先に拾えないか試します
- **クラウド側にも ① を挟む**: クラウドの上位モデルでも曜日を誤ったので、クラウドに渡す前にも日付は Python で確定させます
- **電力をシステム全体で測る**: 今回は GPU ボードだけでした。壁のコンセントで測った値と比べます
