IceRiver AL0 という Alephium 向け ASIC を、自宅の自前フルノードにつなぎました。結論から言うと、AL0 をノードのマイニング API に直接つないでも動きません。間に Stratum ゲートウェイを1枚挟む必要があります。この記事は、その構成と、踏んだ穴と、最後に「そもそも回すべきか」の計算をまとめた記録です。

儲かる話ではないです。むしろ冒頭で書いておくと、2026年8月時点の私の仮置き計算では、AL0 1台は電気代を賄えていませんでした。それでも構成の記録には価値があると思って書いています。

## 先に結論

| 論点 | 答え |
|---|---|
| AL0 をノードの `:10973` に直結できるか | できません。`:10973` は Alephium 独自の TCP プロトコルで、Stratum ではないです |
| 何を挟むか | 公式の `alephium/mining-pool` を単独オーナー用の Stratum ゲートウェイとして使います |
| 報酬はどこに入るか | ノード側の `miner-addresses`（4グループ分の4アドレス）です。ASIC のワーカー名ではないです |
| 公開してよいポートは | P2P の `:9973` だけです |
| 採算 | 2026年8月の仮置き計算では電気代割れ（要検証） |

## 前提と構成

AL0 のプール設定欄は `stratum+tcp://...` 形式です。一方、GPU マイナーが話すのはノードの Mining API（`:10973`）で、これは Alephium 固有の TCP プロトコルです。「ノードのマイニング API にそのまま向ければいい」と書いてあるガイドに従うと、AL0 はここで詰まります。

そこで次の構成にしました。

```text
IceRiver AL0
  └─ stratum+tcp://<LAN内ホスト>:20032
       └─ alephium/mining-pool（rewardEnabled: false）
            ├─ フルノード REST      :12973（localhost のみ）
            ├─ フルノード Miner API :10973（docker network 内のみ）
            └─ Redis               :6379（docker network 内のみ）
```

これは公開プールではなく、LAN 内の単独オーナー用ゲートウェイです。`rewardEnabled` / `paymentEnabled` はどちらも false、wallet は空のままにします。プールはウォレットを持たず、支払いもしません。ブロック報酬はノードのコインベースアドレスに直接入ります。

### 構成要素と検証済みピン

| 要素 | ピン | 備考 |
|---|---|---|
| フルノード | `alephium/alephium:v4.6.0` | 同期済みメインネットノードで AL0 の share 受理を確認（2026-08-02） |
| mining-pool | commit `80d252e`（当時の master） | Mining Protocol v1 |
| Stratum | `:20032` | 公式の single-user 例に合わせたポート |
| 難易度 | `diff: 8` / `minDiff: 1` | 公式 single-user 例の値。AL0 はこの下限を超える share を送ってきました |
| Redis | docker network 内のみ | 外へ出さない |

mining-pool の GitHub Releases は master より遅れているので、リリースタグではなくコミットでピンしています。ノードのイメージを上げるときは、AL0 を向け直す前に、プールが Miner API と話せることを再確認してください。

## 必要なもの

- Docker Engine と Compose
- ディスクは、pruned のメインネットスナップショット前提で空きを200GB超見込んでおくのが現実的です（スナップショット、展開、余裕分）。フルスナップショットはさらに大きいです
- メインネットのアドレスを**4つ、グループ0〜3に1つずつ**
- Stratum しか話さないマイナー（今回は AL0）

アドレスのグループは、自分のノードが無くても公開バックエンドの API で確認できます。

```bash
curl -sS "https://backend.mainnet.alephium.org/addresses/<ADDRESS>/group"
```

## 手順

```bash
cp .env.example .env
# .env を編集：API キー（空なら自動生成）と、4つのマイナーアドレス
./scripts/init-config.sh
./scripts/load-pruned-snapshot.sh   # すでにノードデータがあれば不要
docker compose up -d --build
./scripts/check-synced.sh           # selfReady と synced になるまで待つ
```

その後、AL0 を**1台だけ**ゲートウェイに向けます。商用プールを Pool 2 / Pool 3 に残しておけば、自前ノードが落ちたときのフェイルオーバーになります。

| AL0 の欄 | 値 |
|---|---|
| Pool 1 URL | `stratum+tcp://<Docker ホストの LAN IP>:20032` |
| Wallet / Worker | `<グループ0のアドレス>.rig01` |
| Password | 空 |

ワーカー名の `.rig01` は識別子で、支払い先ではありません。これを勘違いしやすいです。

そして最重要の注意がひとつ。`check-synced.sh` が `synced: true` を出すまで、AL0 の設定を保存しないでください。Miner API がまだ追いついている最中は、プールはジョブを配りません。

## 確認方法

ホスト側でプールのログを追います。

```bash
docker compose logs -f mining-pool
```

設定したワーカー名に対して `Received share`（または同等の行）が出れば成功です。ノード、プール、Redis がすべて `healthy` のままであることも見ます。

ここで線を引いておくと、share はブロックではありません。このキットで確認できたのは、同期済みの v4.6.0 ノードに対して AL0 の share が受理されるところまでです。ブロックを見つけられるかは、運とネットワーク難易度の問題です。

## 穴1. 同期が終わる前に AL0 を向ける

先ほどの繰り返しですが、一番やりやすい失敗です。ノードが同期途中だと、プールはジョブを配りません。つまり share が通らないので、原因がノードの同期にあると気づくまで、ゲートウェイや LAN の設定ばかり疑うことになりがちです。判定は `check-synced.sh` に一本化して、緑になるまで触らないと決めるのが安全でした。

## 穴2. スナップショット取得が途中で死ぬ

ノードを一から同期させると時間がかかるので、公式のスナップショットから始めます。公式ドキュメントは `curl | tar` を1本のパイプで流す形ですが、長い pruned アーカイブでは途中で切れることがありました。

- `HTTP/2 INTERNAL_ERROR`
- その後に `tar: Unexpected EOF`

パイプで流すと、途中で切れた時点で展開も中途半端に終わります。そこで `scripts/load-pruned-snapshot.sh` は次の流れにしました。

1. archives.alephium.org から最新の pruned アーカイブの URL を解決する
2. **HTTP/1.1** かつ**再開付き**でダウンロードする（`curl --http1.1 -C -`）
3. `./data/alephium` に展開する
4. 最後に `chown -R 65534:65534 data/alephium` を促す（コンテナのユーザーが `nobody` のため）

ノードが `synced: true` になったら、tar は消してディスクを空けます。

### コミュニティからも似た報告がありました

2026年8月のネットワーク DoS のあと、同期が崩れたノードが多く出ました。そのときのコミュニティの報告に、「アーカイブの tar は取得中に頻繁に中断するので、再開可能なプロトコルが要る」「最終的に `wget -c` を使った記憶がある」というものがありました（ただし発言者は、そのイメージ自体では試していないと明言しています）。私の `curl -C -` の対策とは方向が一致していますが、サーバーが Range リクエストに対応しているかは私は未確認です（要検証）。

## 穴3. バージョンの選択が一方通行になる

これは自分で踏んだ穴ではなく、同じ時期のコミュニティの報告から知ったことです。ここは一次確認ができていない伝聞なので、そのつもりで読んでください。

2026年8月の DoS のあと、v4.6.0 のノードで同期が `FALLING` / `STALLED` から戻らない例が複数報告されました。次のような情報が出回っていました。

| 報告 | 内容 | 私の確度 |
|---|---|---|
| 回避策 | `user.conf` に `alephium.network.enable-p2p-v2 = false` を足す（v4.6.0 向け） | 設定キー名は発言1件に依拠。公式ドキュメントで未確認（要検証） |
| 排他性 | v4.7.0-test1 は旧 P2P v1 のサポートを削除しており、上の設定を入れると「P2P v1 not supported」で終了する | 運用者1件の報告。再現は未確認（要検証） |
| v4.6.0 での結果 | その運用者の環境では回避策を入れても同期状態は改善しなかった | 1件のみ |

つまり「P2P v2 を切って様子を見る」という切り分けと、「v4.7.0 に上げる」という対処は、同時には取れません。同期不調のノードを触る前に、まず自分がどちらの系に載っているかを確定させるべき、というのがここからの教訓です。

また、v4.7.0 は2026年8月27日にGA（正式リリース）になったと聞いています。そのため、test1 で見られた挙動が正式版でも同じかどうかは未検証です（要検証）。

### 更新で直った例と、その読み方

同じ時期に、v4.6.0 では追いつけなかったノードが v4.7.0-test1 への更新後に16チェーン全てで `BEHIND 0` / `100.00%` / `SYNCED` になったという報告もありました。差分として挙げられていたのは次の2点です。

- 同期に問題が起きたときの自動リトライ（Sync V2 の再試行をスケジュールするログが提示されていました）
- 不正な動作をするピアに対する、より積極的な切断

更新直後の約30分は遅く、そこから速度が乗るという運用者の体感も添えられていました。「良いピアに当たるまで悪いピアを切り続けていたのでは」という推測です。

ただし、この回復が更新単独の効果なのか、スナップショットの再取得との併用の効果なのかは、原文から切り分けられません。同じ運用者が「効いたのはスナップショットを落としてから v4.7.0-test1 を入れたこと」とも述べています。なので私は、「更新が寄与した」までは言えても、「更新だけで直る」とは言えないと考えています（要検証）。

実務上の私のルールは次のとおりです。

1. 同期が止まったら、設定をいじる前にバージョン系を確認する
2. 直らなければ、スナップショットを再取得し、その時点の最新安定版で入れ直す
3. 更新直後の30分程度の遅さだけで失敗と判断しない

## セキュリティ

自宅の機材だからと油断しやすいので、ポートは表にして管理しました。

| ポート | 扱い |
|---|---|
| `:9973/tcp` / `:9973/udp`（P2P） | 公開する。同期のために必要で、インターネットに向けてよいのはこれだけ |
| `:12973`（REST） | `127.0.0.1` に bind。Swagger は `http://127.0.0.1:12973/docs`、ヘッダは `X-API-KEY` |
| `:10973`（Miner API） | 公開しない。docker network 内のみ |
| `:6379`（Redis） | 公開しない。docker network 内のみ |
| `:20032`（Stratum） | ファイアウォールでマイナーのサブネットだけに絞る |

補足が3点あります。

- 複数台の ASIC が同じ送信元 IP（プロキシ）から来る場合は、`config/pool.json` の `maxConnectionsFromSameIP` を上げます。このキットの既定は32です
- mnemonic をプール設定に入れる必要はありません。この単独構成では不要なので、入れないでください
- 上流の mining-pool は Node.js 16 でビルドする構成のままです。LAN 内ソフトとして扱い、ピンしたコミットから再ビルドします。`npm audit fix` を盲目的にかけて、プロトコル互換が保たれていると思い込むのは避けます

## よくある間違い

| # | 間違い | 理由 |
|---|---|---|
| 1 | AL0 を `stratum+tcp://127.0.0.1:10973` に向ける | プロトコルが違う。`:10973` は Stratum ではない |
| 2 | 同じアドレスを4回コピーする | Alephium は4グループ必須。コインベースが不正になるか、マイニングが始まらない |
| 3 | VPS 上で `:20032` を公開する | 監査されていない Node 16 製の公開プールを運営することになる |
| 4 | mnemonic を `pool.json` に入れる | この構成では不要で、漏れたときの被害だけが大きい |

## 採算の計算（助言ではありません）

最後に、冒頭で触れた採算の話です。ここは数字がぶれやすいので、前提を全部書きます。

| 項目 | 値 |
|---|---|
| AL0 の公称ハッシュレート | 約400 GH/s |
| AL0 の公称消費電力 | 約100 W |
| 電気料金（プレースホルダ） | 0.18 USD/kWh |
| 1台の電気代 | 約0.43 USD/日（冷却前） |
| 2026年8月の ALPH 価格 | 約0.027 USD |
| 2026年8月のネットワーク規模 | 約5 PH/s |

100 W を24時間回すと2.4 kWh で、0.18 USD/kWh を掛けると約0.43 USD になります。収益のほうは「受理されたハッシュ量 × ブロック報酬 × ALPH 価格」を難易度で割った形です。2026年8月の価格とネットワーク規模で見ると、AL0 1台は約5 PH/s のネットワークの中で、この電気代を賄えていませんでした。収益側は私の手元で精密に出したものではなく、公称値と当時の相場からの見立てです（要検証）。

結論としては、今日の ALPH 価格とハッシュレートで計算し直してから回すかを決めるのがよいです。すでに止まっている機材なら、止めたままにするのも正当な判断だと思っています。

## まとめ

- AL0 のような Stratum 専用機は、ノードの Miner API ではなく Stratum ゲートウェイにつなぎます
- 公式の `alephium/mining-pool` を単独オーナー用に使い、`rewardEnabled: false` で報酬はノードのコインベースに直接受けます
- 同期完了前に AL0 を向けない。判定はスクリプトに一本化します
- スナップショットは `curl | tar` のパイプにせず、HTTP/1.1 と再開付きで落とします
- 公開するのは P2P の `:9973` だけで、`:20032` はマイナーのサブネットに絞ります
- バージョン系を選ぶ前に、今どちらの系に載っているかを確定させます
- 回す前に、今日の相場で採算を計算し直します
