Claude Code を対話で使うだけでなく、`claude -p`（非対話モード）を Windows のタスクスケジューラから起動して、夜のあいだにメモの整理や検証を進めさせています。5 か月ほど回して分かったのは、**難しいのは「動かすこと」ではなく「正しく終わったと知ること」**でした。先に数字を並べます。

| 実測したこと | 値 |
|---|---|
| 全利用量に占める無人ジョブの比率（42 日・566 セッション） | **3.1%**（対話の最上位モデルが 58.2%） |
| `exit 0` のまま中身が失敗し続けた期間 | **5 週連続**・18 件が未検証のまま「処理済み」 |
| 引数で渡したプロンプトのうち実際に届いた量 | 最初の 1 段落だけ |
| バックグラウンドのサブエージェントが打ち切られるまで | 600 秒 |
| 自動停止したジョブに気づくまで | 3 日 |
| 資格情報の入力待ちで固まった `git push` | 8 日 |

## 前提

環境は[以前の記事](https://zenn.dev/wisteriacorp/articles/wisteria-47f423fb1c16)と同じです。git で管理している Markdown のメモ群（数万ファイル）を、Claude Code が対話と無人の両方で読み書きします。OS は Windows 11、起動はタスクスケジューラです。無人ジョブ用の共通ライブラリを使っているスクリプトは、数えたところ 27 本ありました。

数字はすべて自分の環境での実測で、日付を付けています。Claude Code はバージョンで挙動が変わります。追試するときは、ここに書いた挙動ではなく、手元で測った挙動を信じてください。

## 1. 無人ジョブは利用枠をほとんど食わない

無人化を考えるとき、最初に気になるのは利用枠でした。定期タスクを何十本も回したら、対話で使う分がなくなるのではないか。2026 年 8 月に 42 日分の利用ログを集計した結果は、予想と逆でした。

| 使い方 | 全体に占める比率 |
|---|---|
| 対話（最上位モデル） | **58.2%** |
| 対話（それ以外のモデル） | 31.5% |
| 無人の定期タスク 全部 | **3.1%** |

表は主な区分だけで、合計は 100% になりません。

対話の消費は、94.5% が「キャッシュ済み文脈の読み直し」でした。対話は 1 回応答するたびに、それまでの長い文脈を読み直します。ピーク時の文脈が 40 万トークンを超えた 32 セッションだけで、読み直し全体の 61.1% を占めていました。

無人ジョブはこの逆です。毎回まっさらな文脈で始まり、対象を 1 件か数件に絞って渡すので、文脈が太りません。

ここから決めたことは 2 つです。

1. 枠を節約したいとき、無人ジョブを削っても効きません。効くのは、対話のセッションを作業の単位で切ることです。
2. 対話でやっていた定型作業は、無人へ移すほど得です。対話の文脈が太らなくなります。

この計測のあとにジョブを増やしたので、今の比率は 3.1% より高いはずです。再計測はしていません。

コストが論点でないなら、残る論点は 1 つです。無人で動いたものが正しく終わったと、どうやって知るか。以下はその話です。

## 2. 6 段の型

無人ジョブはすべて同じ型で書いています。骨格だけ示します。

```python
import shutil
import subprocess

MAX_ATTEMPTS = 3
DENY = ["Edit(./.claude/**)", "Edit(./.git/**)", "Edit(./scripts/**)",
        "Bash(git push *)", "Bash(curl *)", "Bash(schtasks *)"]


def run_agent(prompt: str, allowed: str, timeout_sec: int = 900) -> tuple[bool, str]:
    cmd = [shutil.which("claude"), "-p", "--model", "sonnet",
           "--permission-mode", "bypassPermissions",
           "--allowedTools", allowed,            # ③ 通すものを明示
           "--disallowedTools", *DENY,           # ③ 使わせないものは deny
           "--output-format", "text"]
    proc = subprocess.Popen(cmd, stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                            stderr=subprocess.STDOUT, text=True,
                            encoding="utf-8", errors="replace")
    try:
        out, _ = proc.communicate(input=prompt, timeout=timeout_sec)  # ② stdin で渡す
        return proc.returncode == 0, (out or "")[-6000:]
    except subprocess.TimeoutExpired:
        subprocess.run(["taskkill", "/PID", str(proc.pid), "/T", "/F"],
                       capture_output=True)      # ④ プロセスツリーごと止める
        return False, "TIMEOUT"


def main() -> int:
    targets = detect()                           # ① 仕事を数える
    if not targets:
        return 0                                 #    0 件なら起動しない
    attempts = load_attempts()
    for t in targets:
        before = evidence(t)
        run_agent(build_prompt(t), "Read,Grep,Glob,Edit")
        if evidence(t) != before and is_done(t): # ⑤ 戻り値ではなくディスクで判定
            attempts.pop(t.key, None)
            continue
        attempts[t.key] = attempts.get(t.key, 0) + 1
        if attempts[t.key] >= MAX_ATTEMPTS:      # ⑥ 同じ対象で空回りさせない
            retire(t)
    save_attempts(attempts)
    return 0
```

`detect` `evidence` `is_done` `retire` はジョブごとに書きます。`run_agent` の戻り値を、完了判定に使っていない点を見てください。

6 段のどれも、最初からあったわけではありません。それぞれ、事故が 1 つずつ作らせました。

## 3. 各段を作らせた事故

### ① 検出してから起動する

仕事があるかどうかは Python が数えます。0 件なら Claude Code を起動しません。「起動して、モデルに仕事の有無を調べさせる」形にすると、何もない夜にも毎回トークンを使います。待機中のコストをゼロにするのが、この段の役目です。

### ② プロンプトは標準入力で渡す — 5 週間、1 段落目しか届いていなかった

毎週土曜に動く「裏取りジョブ」があります。メモの記述を Web で確かめ、確認できたものに検証済みの印を付けるジョブです。これが 2026-06-13 から 07-11 まで、5 回連続で壊れていました。5 回とも `exit 0` でした。

原因は 3 つ重なっていました。

1. **プロンプトが切れていた。** Windows では `claude` の実体が `claude.cmd`、つまり cmd.exe のバッチです。改行を含むプロンプトを 1 つの引数で渡すと、最初の改行で切れます。モデルに届いていたのは冒頭の 1 段落だけでした。
2. **Web のツールが使えなかった。** 当時、権限確認をスキップするモード（bypass）を指定しただけでは、無人実行で Web 検索と Web 取得が呼べませんでした。呼ぶと「まだ許可されていない」という趣旨の応答が返ります。
3. **スクリプトが `exit 0` を見て「処理済み」と記録していた。** モデルは「検証できませんでした」と丁寧に報告して正常終了します。スクリプトはそれを成功と数え、対象を処理済みの台帳に書きました。台帳に載った対象は、二度と選ばれません。

その結果、毎週数件ずつ、検証されていないメモが検証待ちの列から消えていきました。5 週間、監視は何も言いませんでした。

直したのは 4 点です。

- プロンプトを標準入力で渡します（`communicate(input=prompt)`）。
- 必要なツールを `--allowedTools` に明示します。
- 「処理済み」は証拠があるときだけ付けます。実行の前後でメモを比べ、検証済みのフィールドか新しい出典 URL が増えていたら処理済みです。増えていなければ試行回数を 1 つ足して、次回もう一度選びます。
- 3 回続けて証拠が増えなかった対象は、「未検証のまま退役」と明記して別の扱いにします。「処理済み」とは混ぜません。

誤って処理済みになっていた 18 件は、台帳から外して列に戻しました。

修正のテストには、偽の `claude` コマンドを使いました。標準入力をそのままファイルに書き出すだけのスタブです。日本語を含むプロンプトの全文が届くことを、これで確かめています。本物を起動して「動いたように見える」ことを確かめても、①〜③のどれも検出できません。

### ③ 権限は allow と deny の両方を書き、効き方を実測する

権限まわりは、時期によって逆向きの挙動を観測しました。

| 日付 | 観測 |
|---|---|
| 2026-07-12 | bypass だけでは Web のツールが呼べない。`--allowedTools` に明示すると通った |
| 2026-09-26 | bypass 下で、`--allowedTools` に書いていない Web 取得ツールが実行された。`--disallowedTools` の deny は有効だった |

allow は、ある時期は「書かないと通らない」ものでした。別の時期は「書かなくても通る」ものでした。どちらの時期でも、allow を**絞り込み**として信用することはできませんでした。今は次のように書き分けています。

- 必要なツールは allow に書きます（通らない時期への備えです）。
- 使わせないものは deny に書きます（絞り込みは deny にしか任せません）。
- 効いているかは、無害な禁止コマンドを実際に打たせて、止まるのを見て確かめます。

deny の中身と「なぜ永続化を最優先で塞ぐか」は[セキュリティ対策の記事](https://zenn.dev/wisteriacorp/articles/wisteria-ca987c111d5f)に書きました。ここでは、無人運用で踏んだ書き方の罠を 2 つ足します。

**ルールの種類を間違えると、黙って無視されます。** 設定ファイルに `Write(パス)` の形で書いていた許可ルール 12 件が、一度も効いていませんでした（2026-08-03 に発見）。ファイル操作のルールは `Edit(パス)` で書きます。deny 側で実測したところ、`Edit(パス)` は Write ツールと、Bash からのファイル書き込みも止めました。

**deny は「コマンド名」ではなく「到達手段」で塞ぎます。** 2026-11-04 に、無人ジョブから LAN 内サーバーへの `ssh` を deny に足しました。テスト実行で止められたエージェントは、「絶対パスの `ssh.exe` なら通ります」と迂回路を自分で提案してきました。絶対パスの形と PowerShell 経由の形も、deny に足しています。Bash への deny はベストエフォートです。Bash が要らないジョブでは、Bash ごと deny します。

### ④ timeout とプロセスツリーの kill

固まり方は 2 種類ありました。

**600 秒で打ち切られる。** 無人モードの Claude Code は、バックグラウンドのサブエージェントが残っていると、600 秒待って打ち切ります。2026-09-09 のログに `Background tasks still running after 600s; terminating` が残っていて、その回の前進は 0 件でした。対処は 2 つです。待ちの上限を外す環境変数を設定しました（当時のバージョンでは `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` で効きました）。プロンプトには「サブエージェントは前景で起動する」と書きました。止める役目は、自前の timeout が持ちます。

**8 日間、居残る。** 別のジョブでは、処理の最後の `git push` が資格情報ヘルパーの入力待ちで固まりました。8 日間そのまま残り、ヘルパーは CPU 時間を 6 時間使いました。後続の回は、打ち切られ続けていました。push は非対話の設定にして、120 秒で kill するようにしました。

kill は `taskkill /T /F` で、プロセスツリーごと行います。親だけ止めると、子が残ります。

もう 1 つ、誤診しやすい点があります。ランチャーが出力を一時ファイルに貯めて、終了後にログへ書く作りだと、実行中のログは空です。「ログが出ない」は「固まった」の証拠になりません。

### ⑤ 完了判定はディスク上の証拠で行う

`exit 0` も、モデルの「完了しました」も、引き継ぎ用の要約文も、すべて主張です。証拠は、ジョブの種類ごとに決めます。

| ジョブの種類 | 完了の証拠 |
|---|---|
| 裏取り | 検証済みフィールドの追加、または新しい出典 URL |
| キュー処理 | キューの台帳を実行の前後で比べた差分（前進した件数） |
| 下書きの生成 | 指定したパスにファイルがあり、必須の見出しが揃っている |
| 既存メモの更新 | フロントマターの特定のフィールド |

証拠を決めると、台帳の側の嘘も見つかります。キュー処理を無人化した初日、起動前に台帳と実ファイルを突き合わせると、未処理は 213 件から 175 件に減りました。118 件は、作業が済んでいるのに台帳が古いだけでした。対話なら、食い違いは人に聞けます。無人では聞けません。「実ファイルを真実として台帳を作り直す」処理を、毎回の起動前に入れました。

**「ジョブが触ったファイル」の検出にも罠がありました。** 実行後に変更されたメモを拾って lint にかけています。最初は更新時刻で拾いました。すると、同じ時間帯に動く別のタスクの更新を、このジョブの違反として誤検知しました。今は、実行前に内容ハッシュのスナップショットを取って比べています。細部が 2 つあります。

- 全ファイルのハッシュ計算は 5 分を超えて、使えませんでした。git の HEAD と、未コミットの分だけを対象にしています。
- Windows の作業ツリーは改行が CRLF なので、生のハッシュは git の記録と一致しません。比較には `git hash-object` を使います。

### ⑥ 試行回数で退役させる

同じ対象で 3 回失敗したら、失敗の台帳に移して、以後は選びません。これがないと、決して終わらない 1 件が毎晩トークンを使い続けます。

ジョブ全体にも同じ仕組みを入れています。前進 0 件が 3 回続いたら、ジョブは自分を一時停止して、報告を 1 件出します。ここにも落とし穴が 3 つありました。

1. **1 件の詰まりで夜全体が終わる。** 前進 0 のバッチに当たると、その夜の実行を終える作りにしていました。1 件を 16 分処理しただけで終わった夜がありました。詰まったバッチはその夜だけ飛ばして、次のバッチへ進むように直しました。
2. **前進 0 が正常なジョブがある。** 「出典を確かめられなければ作らない」が正しい挙動のジョブでは、全件見送りが普通に起こります。退役の鍵を「対象の集合のハッシュ」にしました。対象が変われば自動で再開します。同じ対象では空回りしません。
3. **自動停止が見えない。** 一時停止したジョブに、3 日間気づきませんでした。次の章で書きます。

## 4. 型の外側に要るもの

### 4-1. 利用枠のゲート

起動の前に利用量の判定を読み、危険な水準なら起動しません。これは実際に働きました。無人の実行 2 回と対話のセッションが重なった日に、判定が赤に変わり、以後の起動はスキップされました。翌日には自動で戻っています。

設計で決めたことは 2 つです。

- 閾値の計算は 1 か所に置きます。ゲートの側で計算し直すと、2 つの実装がずれます。
- 計測が古いとき、取得に失敗したときは、**起動する側**に倒します。ゲートの故障で全ジョブが止まるほうが、被害が大きいからです。

### 4-2. 実行記録を毎朝 1 行にする

各ジョブは、終わるときに実行記録を 1 行書きます。毎朝のまとめを作る処理が、直近 24 時間分をジョブ別に畳んで、「夜間の無人処理」の 1 行にします。**見えない自動化は、無いのと同じ**です。

ただし、最初の版は「実行した記録」しか出していませんでした。⑥の自動停止に入ったジョブは、実行しないので記録が出ません。出ないことに、3 日間気づきませんでした。「動いた」だけでなく「止まっている」も、同じ場所に出す必要があります。

### 4-3. 作る側と確かめる側を分ける

毎日 1 回、読み取り専用のジョブが動きます。直近 24 時間に無人で書かれた記述から 5 件を抜き取り、元の資料と突き合わせます。重大な食い違いだけを報告します。このジョブには書き込みの権限がありません。作ったジョブ自身に確かめさせても、同じ間違いを繰り返すだけです。

### 4-4. 認証は単一障害点

2026-11-05 の夜から翌朝にかけて、CLI の認証トークンが空になりました。無人ジョブ 5 本が「セッションの期限切れ」で失敗、またはスキップしました。原因は特定できていません。

復旧は対話のログインだけです。コードの貼り付けが要るので、無人では直せません。無人の基盤で、人の手が必ず要る場所はここでした。「複数のジョブが一斉に失敗したら、最初に認証を見る」を、手順の 1 行目に書いてあります。

### 4-5. 対話のセッションから入れ子で起動しない

対話中の Claude Code から無人ジョブのスクリプトを直接叩くと、入れ子になった `claude -p` がハングします。動作確認は、タスクスケジューラ経由で起動して行います。

対話から無人へ仕事を渡したいときのために、「依頼ファイルを置くフォルダ」を作りました。15 分ごとに動く汎用のジョブが、1 件ずつ取り出して実行します。対話の側は、依頼を書いて置くだけです。

## 5. 無人にしないこと

無人のジョブは質問できません。プロンプトの先頭に、次のルールを載せています。

- 迷う対象は触らない
- 強制のオプション（`--force` の類）を使わない
- 削除と移動をしない
- 信頼度の低い素材から、人物に関するメモを新しく作らない

逆向きの失敗もありました。最初の頃、無人ジョブがファイルを 1 件も書けなかったことがあります。そこから「無人は読み取り専用」と一般化して、検知と通知だけを行うジョブを増やしました。人に戻す設計です。実際の原因は、②の事故と同じ権限の与え方の誤りでした。直したあとは、無人で書けています。失敗を設計の前提に格上げする前に、原因を 1 段掘るべきでした。

## まとめ — 持ち帰れるチェックリスト

1. 仕事を数えてから起動する。0 件なら起動しない
2. プロンプトは標準入力で渡す。届いた全文を、偽のコマンドで確かめる
3. allow と deny の両方を書く。絞り込みは deny に任せ、効き方を実測する
4. timeout をかけ、プロセスツリーごと止める。`git push` のような対話待ちになりうる処理にも上限を付ける
5. 完了は、ディスク上の証拠で判定する。`exit 0` と「完了しました」は主張として扱う
6. 同じ対象の失敗は、回数で退役させる。「処理済み」と「未完のまま退役」を混ぜない
7. 実行記録と停止状態を、毎朝読む場所に出す
8. 作るジョブと確かめるジョブを分ける
9. 一斉に失敗したら、最初に認証を見る

特別な技術は 1 つもありません。どれも、`exit 0` を信じて失敗したあとに足した点検です。

個人の AI 基盤の全体像は[こちら](https://zenn.dev/wisteriacorp/articles/wisteria-47f423fb1c16)、権限と秘密の守り方は[こちら](https://zenn.dev/wisteriacorp/articles/wisteria-ca987c111d5f)にまとめています。
